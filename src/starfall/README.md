# Starfall: API и игровая логика

## Socket.IO

Модуль регистрирует `StarfallGateway` (`@nestjs/websockets` и `@nestjs/platform-socket.io` версии 9, Socket.IO 4) и `StarfallRealtimeService`. Namespace `/starfall`, path `/socket.io`, только транспорт `websocket`, без HTTP long-polling. REST API и DTO не меняются.

Клиент передаёт `auth: { token, gameId }`. Middleware проверяет подпись/срок JWT через `ACCESS_SECRET`, наличие пользователя в БД и участие через `getGameView`. Только после этого сокет включается в `game:<gameId>`. Игрок определяется по JWT; произвольных клиентских join/emit-команд нет. Посторонний читает публичное HTTP-лобби, но не подписывается на игру до HTTP join.

После входа в комнату сервер повторно читает состояние и отправляет `game:state`, исключая потерю изменений между первым чтением и подпиской. После сохранённого join или команды сервис вызывает publisher вне блока валидации/записи. Выбираются только сокеты комнаты игры; каждому отправляется его `game.getViewFor(playerId)`, как в HTTP GET, включая все вкладки обоих игроков. Внутренний snapshot, чужая рука и закрытые колоды не передаются. Повтор обработанного commandId/join участника не рассылает дублирующее событие. Конфликты и неуспешное сохранение не рассылаются.

Ошибки handshake приходят как `connect_error` с `data.status`; ошибки открытого соединения — `game:error` с `{ status }`. При истечении JWT отправляется 401 и сокет отключается. Клиент обновляет токен через существующий HTTP refresh и переподключается. При ошибке доставки сохранённая команда не превращается в HTTP-ошибку: ошибка логируется, сокеты комнаты отключаются для повторной синхронизации. Клиент игнорирует снимки меньшей версии. Гарантии хранения/повторной доставки отдельных событий нет; reconnect получает актуальный снимок.

Backend запускается долгоживущим NestJS-процессом на текущем HTTP-порту. Reverse proxy обязан проксировать `/socket.io/` с WebSocket Upgrade. `CLIENT_URL` сохраняет назначение frontend origin. Serverless Vercel из существующей конфигурации не заменяет такой Socket.IO-сервер. Для нескольких процессов нужен общий Socket.IO adapter, например Redis: стандартный in-memory adapter изолирует комнаты внутри одного процесса. Инфраструктура развёртывания здесь не изменяется.

`starfall-realtime.spec.ts` поднимает настоящий NestJS HTTP/WebSocket-сервер на случайном localhost-порту. Используются реальные JWT/Passport, controller, gateway, service и движок; Prisma заменена памятью. Проверяются автостарт через HTTP join, рассылка HTTP-команды обоим игрокам и дополнительной вкладке, совпадение с приватным GET, изоляция другой игры, reconnect, запрет постороннего/неизвестного пользователя и неверного/просроченного JWT, истечение JWT открытого сокета. Реальный PostgreSQL и production proxy не проверяются.


## Партия и авторизация

Все `/api/starfall/*` требуют JWT. `POST games` создаёт ожидающую партию с создателем. `GET games?notStarted=true` возвращает ожидающие партии и имена участников. `GET games/:gameId/lobby` доступен до присоединения и возвращает только id, status, version, startingHp и игроков `{ id, username }`.

`POST games/:gameId/join` принимает `expectedVersion`. Присоединение второго игрока и запуск партии происходят в одной команде с одной записью и optimistic lock. Первого игрока выбирает сервер через `crypto.randomInt`; он получает три карты, второй — пять. Повторный join участника возвращает актуальное приватное состояние без изменения версии. Отдельного `/start` нет.

`GET games/:gameId` и `POST games/:gameId/commands` доступны участникам. В приватном состоянии есть только собственная рука; чужая рука и закрытые колоды представлены счётчиками. Данные имён загружаются через связь `StarfallGame.players` вместе со снимком в `getGame`: выбираются только `id` и `username`. `GameEntity` хранит имена в памяти по ID и использует их в публичном списке участников и приватном представлении; в JSON-снимок имена не попадают. Создание возвращает связь из `create`, присоединение — из `update` после подключения второго участника. Обычные команды используют уже загруженные имена без повторной загрузки связи при записи; `privateView` синхронен и не обращается к БД. Отдельного `user.findMany` нет. Это один вызов Prisma для загрузки партии со связью, но не гарантия одного SQL-запроса: загрузкой relations управляет установленная версия Prisma. Ошибки отсутствия участия — 403, отсутствия партии — 404, конфликта версии — 409. Неверная команда — 400.

## Команды и представление

Команды: play_card, buy_card, use_ability, resolve_pending, cancel_pending, attack_base, attack_player, end_turn. Каждая содержит commandId, expectedVersion, type, payload. Повтор обработанного commandId возвращает текущее состояние; сохранение проверяет пару id/version.

Приватное представление дополнено:

- `explorer`: доступный экземпляр Explorer или null; существующий buy_card принимает его ID. `explorersCount` сохраняется.
- `username` у игроков; существующий `nextShipToTop` только у владельца.
- `copiedCardId` и `abilityStates` у карт: id/kind/action/isUsed/isAvailable из существующих Ability и canUseCardAbility. Доступность учитывает активную партию, владельца, ход и отсутствие pending action; сама команда независимо повторяет проверки.

Движок хранит nextShipToTop, copiedCardId и usedAbilities в JSON-снимке. Копирование восстанавливается по ID исходной карты среди всех зон, включая scrapped; поиск фракции использует тот же набор. HP ограничено снизу нулём, летальный урон завершает игру существующим finishGame. Утилизация при отсутствии карт в разрешённых зонах не создаёт невыполнимый pending action; последовательность продолжается.

## Автоматические союзные способности

`Ability.isAutomaticAlly` разрешает автоматическое исполнение только для `ally` без выбора текущего игрока: бой, торговля, влияние, добор, добор за фракцию, начисление сброса сопернику, следующий корабль наверх колоды и эффект союзника всех фракций. `sequence` и `if_bases_in_play` проверяются рекурсивно: все вложенные действия должны быть без выбора. Неизвестные действия, выбор цели/карты/эффекта и смешанные последовательности остаются ручными, даже при одной или нуле доступных целей. Основные и Scrap-способности этим механизмом не активируются.

`GameEntity` проверяет весь свой стол после розыгрыша корабля или базы, ручного использования способности, завершения выбора и начала хода. Сначала обходятся базы, затем корабли, способности — в порядке списка. Используются существующие проверки союзников (включая Mech World и Stealth Needle), исполнение и `usedAbilities`. Уже использованная способность повторно не применяется; базы получают новые применения после сброса состояния в начале своего хода.

При `pendingAction` автоматизация ждёт окончания всей цепочки выбора, включая выбор от скопированной основной способности и обязательный сброс в начале хода. Разрешённая отмена выбора также продолжает цепочку. Эффект сброса сопернику начисляется автоматически, сам соперник выбирает карты в начале своего хода.

Автоматические эффекты сохраняются и рассылаются в рамках исходной команды с одним увеличением версии. В DTO достаточно существующих `isUsed`/`isAvailable`, формат снимка и схема БД не меняются. GET и восстановление снимка ничего не активируют; для старых партий проход произойдёт при следующем перечисленном игровом действии. Повтор `commandId` не начисляет бонусы повторно.

## Проверки и границы

Jest-набор Starfall проверяет движок, DTO команд и сервис с Prisma mock: исходные правила, новые поля, автостарт, конкурентный join, приватность, повторы, overkill, копирование после утилизации оригинала и отсутствие целей утилизации.

Для автоматических союзных способностей проверяются оба порядка розыгрыша, отсутствие повторного начисления, ресурсы/добор/влияние/сброс сопернику, базы на следующем ходу, Mech World, копирование с вложенным выбором и восстановлением снимка, ручные выборные и смешанные эффекты. Тест сервиса проверяет сохранение и публикацию всех бонусов одной командой, совпадение с GET и идемпотентный повтор.

2026-11-26: проходят 71 тест Starfall, включая 7 HTTP/WebSocket-тестов с разрешённым локальным портом, и проверка типов по `tsconfig.build.json`. Полная `tsc --noEmit --incremental false` даёт те же 46 ошибок в прежних e2e-тестах других модулей, что и исходная версия; новых ошибок нет. ESLint изменённых файлов не сообщает ошибок; остаются прежние предупреждения о non-null assertions.

Браузерная интеграция фронтенда дополнительно проверялась с настоящими Nest-контроллером, DTO и сервисом, но временными авторизацией и хранилищем в памяти. Это не проверка PostgreSQL/JWT в развёрнутом окружении. Миграция схемы БД для изменений не требуется.

Тесты загрузки имён дополнительно проверяют создание/join, обычные и повторные команды, актуальное имя после изменения User, сопоставление по ID независимо от порядка relation и отсутствие имён в JSON-снимке.
