# Starfall: API и игровая логика

## Партия и авторизация

Все `/api/starfall/*` требуют JWT. `POST games` создаёт ожидающую партию с создателем. `GET games?notStarted=true` возвращает ожидающие партии и имена участников. `GET games/:gameId/lobby` доступен до присоединения и возвращает только id, status, version, startingHp и игроков `{ id, username }`.

`POST games/:gameId/join` принимает `expectedVersion`. Присоединение второго игрока и запуск партии происходят в одной команде с одной записью и optimistic lock. Первого игрока выбирает сервер через `crypto.randomInt`; он получает три карты, второй — пять. Повторный join участника возвращает актуальное приватное состояние без изменения версии. Отдельного `/start` нет.

`GET games/:gameId` и `POST games/:gameId/commands` доступны участникам. В приватном состоянии есть только собственная рука; чужая рука и закрытые колоды представлены счётчиками. Данные имён загружаются через связь `StarfallGame.players` вместе со снимком в `getGame`: выбираются только `id` и `username`. `GameEntity` хранит имена в памяти по ID и использует их в публичном списке участников и приватном представлении; в JSON-снимок имена не попадают. Создание возвращает связь из `create`, присоединение — из `update` после подключения второго участника. Обычные команды используют уже загруженные имена без повторной загрузки связи при записи; `privateView` синхронен и не обращается к БД. Отдельного `user.findMany` нет. Это один вызов Prisma для загрузки партии со связью, но не гарантия одного SQL-запроса: загрузкой relations управляет установленная версия Prisma. Ошибки отсутствия участия — 403, отсутствия партии — 404, конфликта версии — 409. Неверная команда — 400.

## Команды и представление

Команды: play_card, buy_card, use_ability, resolve_pending, cancel_pending, attack_base, attack_player, end_turn. Каждая содержит commandId, expectedVersion, type, payload. Повтор обработанного commandId возвращает текущее состояние; сохранение проверяет пару id/version.

Приватное представление дополнено:

- `explorer`: доступный экземпляр Explorer или null; существующий buy_card принимает его ID. `explorersCount` сохраняется.
- `username` у игроков; существующий `nextShipToTop` только у владельца.
- `copiedCardId` и `abilityStates` у карт: id/kind/action/isUsed/isAvailable из существующих Ability и canUseCardAbility. Доступность учитывает активную партию, владельца, ход и отсутствие pending action; сама команда независимо повторяет проверки.

Движок хранит nextShipToTop, copiedCardId и usedAbilities в JSON-снимке. Копирование восстанавливается по ID исходной карты среди всех зон, включая scrapped; поиск фракции использует тот же набор. HP ограничено снизу нулём, летальный урон завершает игру существующим finishGame. Утилизация при отсутствии карт в разрешённых зонах не создаёт невыполнимый pending action; последовательность продолжается.

## Проверки и границы

Jest-набор Starfall проверяет движок, DTO команд и сервис с Prisma mock: исходные правила, новые поля, автостарт, конкурентный join, приватность, повторы, overkill, копирование после утилизации оригинала и отсутствие целей утилизации.

Браузерная интеграция фронтенда дополнительно проверялась с настоящими Nest-контроллером, DTO и сервисом, но временными авторизацией и хранилищем в памяти. Это не проверка PostgreSQL/JWT в развёрнутом окружении. Миграция схемы БД для изменений не требуется.

Тесты загрузки имён дополнительно проверяют создание/join, обычные и повторные команды, актуальное имя после изменения User, сопоставление по ID независимо от порядка relation и отсутствие имён в JSON-снимке.
